# Prisoners DAOlemma Tournament: Implementation Log & Corrections

Companion document to `prisoners-daolemma-tournament-decisions-v1_0.md`, `prisoners-daolemma-discord-replacement.md`, and the `integration/` tree. Written from a separate independent build session working from the same frozen spec — includes verified implementation detail, one architecture deviation (with rationale), and a punch list of concrete fixes found while actually building against this spec. No wallet addresses, private keys, or other secrets included; see `integration/shared/runtime-source.json` for the canonical public contract addresses.

## What this session verified independently, that matched the frozen config exactly
Before finding `integration/shared/runtime-source.json`, this session independently derived the same game/auth-adapter/identity-registry addresses and the same `expected_owner` by querying Base Sepolia directly and cross-referencing the existing 32-player canary evidence bundle. Also independently confirmed the local game-repo checkout was exactly the pinned revision. Noted here as a cross-validation data point, not a new finding.

## Deviation from the frozen spec: log-based chat instead of Discord
Before finding `prisoners-daolemma-discord-replacement.md`, this session independently arrived at the same conclusion — replace Discord with an orchestrator-owned append-only log — for the same reason (agents only ever act on a poke; an always-on external chat app adds a dependency without adding capability). The frozen replacement doc's refinements (separate per-team JSONL logs, `requestId`-keyed idempotency, an explicit cross-team fairness protocol, and the hard boundary that chat has zero causal influence on phase transitions or transactions) were adopted as-is rather than re-derived.

## Corrections found while implementing

1. **Wallet env var name**: the game CLI's `resolveSignerWallet()` reads `GAMEPLAY_WALLET_PRIVATE_KEY` specifically — a generic `WALLET_PRIVATE_KEY` will not be picked up. Confirmed by reading `authTooling.js`/`gameTooling.js` directly.
2. **Foundry is not required for the register/join/commit/reveal/claim pipeline.** Only wallet *generation* (`generateKeystore.js`) and key *reveal* (`revealPK.js`) shell out to `cast` in the pinned game repo — the actual signing path (`resolveSignerWallet`, `ethers.Wallet.fromEncryptedJson`) is plain `ethers`. A wallet-generation script producing standard V3 keystores (same format `cast wallet import` writes) removes the Foundry dependency entirely, verified live against a real ERC-8004 `status` query with zero `cast` involved.
3. **`maritime logs` flag is `-n`/`--lines`.**
4. **`EffectiveChoiceMaterialized` event** carries `defaultedCommit`/`defaultedReveal` flags directly — cleaner source than inferring from tx presence for distinguishing "defaulted to Share" from "chose Share," which matters because the two look identical in `rounds.json` otherwise and corrupt any behavioral read of the demo if conflated.
5. **Sleep/wake latency has a second-order effect beyond an individual agent's move defaulting.** `canAdvancePhase` only returns true early once `committedCount == aliveCount` (or `revealedCount == committedCount`) — a single slow/sleeping agent doesn't just default its own move, it forces the *entire round* to wait out the full block deadline instead of early-advancing. With 10 independent containers, at least one lagging per round is a realistic expectation. Recommend sizing the commit/reveal deadline close to the actual target round-time ceiling rather than leaving it generously large "as a rare fallback" — the fallback path isn't rare enough at this scale to treat that way. Also recommend a bounded poke-timeout-and-retry policy so one slow agent doesn't block the others' pokes.
6. **Funding threshold should cover the full expected round count, not just the entry fee.** Entry fee is paid once at join; a full game needs a commit + reveal tx per round for up to ~5 rounds. A wallet funded for "entry fee + a little" can run out of gas mid-series, and a failed tx from insufficient funds is indistinguishable from deliberate non-participation unless specifically checked for.
7. **"Series winner" needs an explicit per-game attribution rule the spec doesn't define**, because the contract itself is not team-aware. A single game's winner set (from `payouts.json`) can span both teams — verified against the real 32-player canary export, where the historical winner set actually did split evenly across both causes. "Series winner = team with more game wins" silently assumes each game resolves to one team, which the contract does not guarantee. Recommend an explicit rule (e.g., majority-of-winners-by-count, with an exact tie or no-winner/cancelled outcome counted as a wash) encoded in the scoring layer rather than left implicit.
8. **Pre-declare metrics before the game runs, not after.** Deciding what to measure after seeing the data undermines the point of the comparison. A minimal fixed set: cooperation rate (share vs. steal/catch across rounds), first-defection round, and negotiation-vs-move divergence.
9. **Key hygiene, made concrete rather than just noted as a risk**: a private-key-shaped-string grep (`0x` + 64 hex chars) across every log/state/evidence file before anything is shared, and an explicit key-destruction step once a run's games are done (testnet wallets are disposable — don't reuse them for anything else).
10. **A crude spend/token circuit breaker is worth building now, not deferring.** Ten self-signing, self-directed agents running unattended during a live run is a real near-term runaway-spend risk (a retry loop, a confused agent hammering the API) — a running counter with a hard stop past an agreed ceiling is cheap insurance.
11. **Commit each agent's system/context-setting prompt to the repo** as a reviewable artifact — both templates need the same rules (game mechanics, valid moves, the "block" = Catch vocabulary note, expected output format) communicated the same way; this is the actual mechanism for eliciting comparable behavior from two different frameworks, not something to improvise per-agent at build time.

## Solo-or-pair note
The build sequence and integration checkpoints in the existing planning docs assume a small team. They degrade cleanly to a single person working sequentially — the main adjustment is that checks originally designed as "the other person catches your mistake" (team/cause mapping verification, model-parity re-check) need to become automated scripts/assertions instead of a manual second glance, since solo there's no second person to provide that check.
